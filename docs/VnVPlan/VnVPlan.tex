\textbf{Andreas:}
\begin{enumerate}
	\item When writing this deliverable, our team worked well to divide the 
	work required evenly, and ensure that all team members contributed to each 
	important section of the document. This helped us to ensure that critical 
	sections were developed by taking all team members' ideas and contributions 
	into account. Specifically, instead of having one team member focus on 
	writing a large swath of system tests, and making other members focus on 
	most of the general plan sections of the document (SRS verification, etc.), 
	all users contributed to the system tests, ensuring that our ideas and 
	perspectives were combined to cover the system's requirements as much as 
	possible.
	\item One pain point I experienced during the deliverable was attempting to 
	find a balance between feasibility and coverage when writing system tests. 
	When creating a plan to test the system as a whole, our goal was to cover 
	all requirements mandated in the SRS, and extensively test the system so 
	that it is verified and validated as a professional engineering product. 
	However, since the project's development must fit in an eight month scope 
	(of which there are approximately five to six months remaining), with 
	verification 
	activities likely being allotted a fraction of that time (to fit with other 
	development activities), the plan for testing must be scoped to be feasible 
	in the project's context. This balance was found by ensuring that the 
	system tests I wrote minimally cover the requirements provided in the SRS, 
	and any other system qualities that must be tested, but do not necessarily 
	have to extend into a large, complex set of tests across a large sample 
	size. For example, while primary playtests (usability tests) for the 
	software are planned, the number of participants in these tests and the 
	amount of testing they must participate in is given a conservative bound, 
	to ensure feasibility. However, if extra time and resources are available 
	in the project to complete more testing, the scope of the tests planned can 
	be increased to ensure better coverage.
	\item One skill I will personally need to acquire is a proficiency with 
	unit testing Godot game engine code. Since Godot has been selected as the 
	game engine that will be used for the development of the project's 
	software, its capabilities for unit testing its GDScript language must be 
	used to implement automated unit testing. Additionally, I will need to 
	acquire the skill of executing automated unit tests of GDScript code with 
	GitHub Actions or CI/CD pipelines, since it is required for the project.
	\item For both skills above, the knowledge required to improve my 
	proficiency could be found from video tutorials (on YouTube, for example), 
	official Godot tutorials and documentation, or from being taught by other 
	team members or peers with experience with Godot. In my case, I will 
	primarily use the official Godot tutorials and documentation to learn these 
	skills, as official sources tend to have the most accurate information for 
	the exact version of the game engine we will use in the project. 
	Additionally, not relying on others for instruction related to the skills 
	(while help can still be acquired from team members or peers occasionally) 
	can help me to efficiently learn the skills required asynchronously.
\end{enumerate}
