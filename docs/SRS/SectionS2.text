\subsection*{\textbf{Physical Controls:}}
\textcolor{purple}{\textbf{Functional Requirements:}}
\requirement{SFR}
{The controller button-bindings shall have a keyboard and mouse equivalent.}
{The user must have full access to all functionality of the game with either a controller or keyboard and mouse. This helps if the user is not experienced or comfortable with a controller option.}
{The directional inputs of the d-pad from the controller has the same input mappings as the left, right, up, down on the keyboard. The A, B, X, Y, L and R buttons on 
XBOX controllers also have a keyboard equivalent functionality mapped into certain keys.}
{Satisfies \ref{controller-constraint}, Refines \hyperlink{UC-001}{UC-001}, \hyperlink{US-001}{US-001}, 
Satisfied by \ref{controller-marking}, \ref{controller-default}, \ref{controller-switching},}
{controller-equivalence}

\requirement{SFR}
{The game shall explain what each button on the connected controller can do for the user. The same goes for the keyboard and mouse (see \ref{controller-equivalence}).}
{Identifying the actions of what each button will do will prevent the player from feeling lost or accidentally doing an action that was not intended.}
{The game displays a diagram of a controller that marks all the actions with correlated button.}
{Satisfies \ref{controller-equivalence}, Refines \hyperlink{UC-001}{UC-001}, \hyperlink{US-001}{US-001},}
{controller-marking}

\requirement{SFR}
{The game shall default to the keyboard and mouse as the main source of input handling.}
{A keyboard and mouse is much more likely to be connected successfully since the software will be design to run on a computer.}
{During the launch of the software, the software will accept keyboard key inputs and the user will have to manual switch to the controller.}
{Satisfies \ref{controller-constraint}, \ref{controller-equivalence}, Refines \hyperlink{UC-001}{UC-001}, \hyperlink{US-001}{US-001}
Satisfied by \ref{controller-onlyone},}
{controller-default}

\requirement{SFR}
{The game shall give the option for the user to switch between using a controller or keyboard and mouse as inputs.}
{This gives the player and the game knowledge of how the inputs are being handled whether via keys or controller buttons.}
{During the start screen, there is an option to change from the default keyboard and mouse or connected controller.}
{Satisfies \ref{controller-constraint}, \ref{controller-equivalence}, \ref{controller-default}, Refines \hyperlink{UC-001}{UC-001}, \hyperlink{US-001}{US-001}
Satisfied by \ref{controller-onlyone},}
{controller-switching}

\requirement{SFR}
{The game shall only handle either a keyboard and mouse or controller inputs at a single instance, not both at same time.}
{If a controller and keyboard is connected, then this prevents the user from accidently pressing inputs that were not intended.}
{During the launch of the software, if a controller is connected the game will not accept any action from it unless switched to.}
{Satisfies \ref{controller-default}, \ref{controller-switching}, Refines \hyperlink{UC-001}{UC-001}, \hyperlink{US-001}{US-001}}
{controller-onlyone}

\subsection*{\textbf{Game Settings:}}
\textcolor{purple}{\textbf{Functional Requirements:}}

\requirement{SFR}
{The game shall have a configuration that changes the player starting health.}
{This a difficulty setting to test how far a user can last on average before failing and restarting a run. For example, a user with minimum gaming experience
will typically have a better time with the game if the user can last a little longer. Dialing the health will also limit how far a player goes on their initial runs, thus
preventing them from seeing too much of the game early on. Having this configuration will help to see the balance between player overall experience versus
the pace at which the content of the game is consumed at.}
{The user can change the starting health from a minimum of 50 to 150.}
{Refines \hyperlink{UC-001}{UC-001}, \hyperlink{UC-002}{UC-002}, \hyperlink{UC-003}{UC-003},
Satisfied by \ref{game-variant-lock}, \ref{game-better-experience}, \ref{game-variant-description}}
{game-variant-health}

\requirement{SFR}
{The game shall have a configuration that changes the average amount of resources gained after an encounter.}
{This is a pacing mechanic for the game. The user should not be able to purchase all the upgrades from the central hub with only a short few runs, otherwise,
the initial difficulty of the game gets trivialized from the added upgrades, not from the player's own skill. Having this configuration will also help distinguish
how a long the average player feels about the overall pace of game; different users have varying tolerances between the feeling of progression and grinding over and
over again.}
{The user can change the average of resources dropped between 10 to 20 between enemy encounters.}
{Refines \hyperlink{UC-001}{UC-001}, \hyperlink{UC-002}{UC-002}, \hyperlink{UC-003}{UC-003},
Satisfied by \ref{game-variant-cost}, \ref{game-variant-lock}, \ref{game-variant-description}}
{game-variant-droprate}

\requirement{SFR}
{The game shall have a configuration that changes the cost of each purchasable upgrade.}
{Changing the purchase cost is slightly different from \ref{game-variant-droprate}, because it changes how players perceive the purchase progression. 
A player will gauge how far he or she has to go before the being able to purchase a new upgrade. If the cost is too high, then this discourages the player
from ever buying it. If the cost is too low, then this runs the risk of completing all purchase too fast; there needs to be a balance for the cost.}
{The user can change the additional cost of each purchasable  upgrade from zero to 50.}
{Satisfies \ref{game-variant-droprate}, Refines \hyperlink{UC-004}{UC-004}, \hyperlink{US-004}{US-004},
Satisfied by \ref{game-variant-lock}, \ref{game-better-experience}, \ref{game-variant-description}}
{game-variant-cost}

\requirement{SFR}
{The game shall prevent the user from changing the game's configurations until starting a new game.}
{Changing and altering the game's parameters whilst in-game trivializes the idea of game variants entirely. If a user changes a configuration then it could be because of inconvenience,
and thus ruins the idea of difficult and a stable game experience. This is also to prevent bugs due to changing variables. For example, changing the
initial starting health while the game states the current health is zero.}
{The game will not including an option to allow the user to stop the game and immediately change a setting such as initial starting health.}
{Satisfies \ref{game-variant-cost}, \ref{game-variant-droprate}, \ref{game-variant-health}, Refines \hyperlink{UC-002}{UC-002}, \hyperlink{UC-002}{UC-002}, \hyperlink{US-001}{US-001}, \hyperlink{US-002}{US-002},
Satisfied by \ref{game-variant-confirm}}
{game-variant-lock}

\requirement{SFR}
{The game shall give a prompt for confirmation once the user has finished the setting up the game's configurations.}
{The game's configurations cannot be changed (see \ref{game-variant-lock}). This gives the user a contractual  obligation to finish the game whilst under the rules laid out. }
{When a user exits from the configurations menu, the game will display a prompt showing the question "Is the configuration complete" followed by 'yes' or 'no' text buttons.}
{Satisfies \ref{game-variant-lock}, Refines \hyperlink{UC-002}{UC-002}, \hyperlink{UC-002}{UC-002}, \hyperlink{US-001}{US-001}, \hyperlink{US-002}{US-002}}
{game-variant-confirm}
